# 阶段 15：用户体系

> 15.1 后端认证基础 / 15.2 数据云端化 / 15.3 前端认证 均记录于本文档。
> 本文档随子步骤逐步更新。

## 背景思考

15.1 完成了账号与认证（注册/登录/JWT），但用户的生词本、收藏、阅读记录还全部存在浏览器 localStorage 里——换设备就没了，而且这些数据没有归属。15.2 的目标是把这三类个人数据搬到后端数据库，按 `user_id` 隔离，为后面前端登录后自动同步做准备。

设计时尽量对齐前端已有的数据结构，避免后面 15.4 做切换时来回改：

- 生词 `VocabEntry` 里的 FSRS 卡片（`card` 字段）是一个嵌套对象，用 JSON 列直接存
- 阅读记录是"一篇文章一条"（upsert 语义），前端 `saveProgress` 是覆盖写
- 收藏是 `number[]`（文章 id 列表）

## 完成内容

**模型（`models.py`）**：新增三张表，全部带 `user_id` 外键（级联删除）：

| 表 | 唯一约束 | 说明 |
|---|---|---|
| `vocabulary_entries` | `(user_id, word)` | 生词：word/phonetic/definition/source_title/added_at/card(JSON) |
| `bookmarks` | `(user_id, article_id)` | 收藏：user_id + article_id + created_at |
| `reading_records` | `(user_id, article_id)` | 阅读：read_at + progress(0~1) |

建表直接复用 `seed()` 里的 `Base.metadata.create_all(engine)`——幂等，已有表不会动，新表自动创建。

**Schema（`schemas.py`）**：`VocabCreate/VocabUpdate/VocabOut`、`BookmarkOut`、`ReadingIn/ReadingOut`、`MeData`（一次拉全量）。注意 `VocabOut`/`BookmarkOut`/`ReadingOut`/`UserOut` 都加了 `from_attributes=True`。

**路由（`api/routes/me.py`，prefix `/api/me`）**：

- `GET /api/me/data`：一次返回 user + 生词 + 收藏 id 列表 + 阅读记录（15.4 前端登录后一次性拉全量用）
- 生词：`GET/POST /api/me/vocabulary`、`PATCH/DELETE /api/me/vocabulary/{word}`
- 收藏：`GET /api/me/bookmarks`、`POST/DELETE /api/me/bookmarks/{article_id}`
- 阅读：`GET /api/me/reading`、`PUT /api/me/reading/{article_id}`（upsert）、`DELETE`

全部走 `get_current_user` 依赖，无 token / 坏 token 一律 401。

## 技术决策及理由

1. **JSON 列存 FSRS 卡片**：card 是 ts-fsrs 的序列化对象，结构固定且小，SQLite 的 JSON 列存进来就是文本，Pydantic `dict` 类型直接映射，最省事。因为每次都整卡覆盖写（PATCH 传整个 card），不需要 SQLAlchemy 的 `MutableDict` 追踪。
2. **阅读记录用 upsert（PUT 幂等）**：前端语义就是"这篇文章读到 50%"覆盖写，天然一篇文章一条；`(user_id, article_id)` 唯一约束兜底。
3. **`/api/me/data` 合集接口**：登录后前端只要发一个请求就能恢复全部个人数据，避免 3 个请求各拉一次（对个人项目意义不大，但 15.4 切换逻辑会简单很多）。
4. **`from_attributes=True` 的三张 schema**：踩了个坑（见下），手动构造嵌套 `MeData` 时 FastAPI 不会自动给嵌套模型开 ORM 转换。

## 踩坑记录

**FastAPI 嵌套响应模型不会自动 from_attributes**。`GET /api/me/data` 直接 500：

```
ValidationError: 1 validation error for MeData
user
  Input should be a valid dictionary or instance of UserOut [type=model_type, input_value=<app.models.User object ...>]
```

原因：FastAPI 只在**最外层** response_model 帮你开 `from_attributes=True`；`MeData` 是我手动 `MeData(user=ORM对象, ...)` 构造的，里面嵌套的 `UserOut`/`VocabOut` 走的是模型自己的配置，没有开 ORM 转换，于是把 ORM 对象当成非法输入。

解决：给 `UserOut`/`VocabOut`/`BookmarkOut`/`ReadingOut` 都显式加 `model_config = ConfigDict(from_attributes=True)`。

**新路由没生效的假警报**：用 `app.routes` 检查路由时只看到 5 条（openapi/docs/health），差点以为 include_router 没生效。实际是这版 FastAPI 把挂载的路由包成 `_IncludedRouter` 惰性展开，`r.path` 是 `None`，被我过滤掉了。**教训：检查路由别用 `r.path` 集合法，直接看总数或 curl 接口。** 重启 uvicorn（非 `--reload` 启动）后接口一切正常。

## 实际命令

```bash
# 登录拿 token
curl -X POST localhost:8000/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"tester@example.com","password":"secret123"}'

# 生词 CRUD
curl -X POST localhost:8000/api/me/vocabulary -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"word":"harbinger","source_title":"The Atlantic"}'
curl -X PATCH localhost:8000/api/me/vocabulary/harbinger -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"card":{...FSRS...}}'
curl -X DELETE localhost:8000/api/me/vocabulary/harbinger -H "Authorization: Bearer $TOKEN"

# 收藏 / 阅读
curl -X POST localhost:8000/api/me/bookmarks/1 -H "Authorization: Bearer $TOKEN"
curl -X PUT localhost:8000/api/me/reading/1 -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"progress":0.5}'
curl localhost:8000/api/me/data -H "Authorization: Bearer $TOKEN"
```

验证过的分支：注册→重复 400、登录→me、生词增改删、收藏增删+404、阅读 upsert（改 progress 同一条）、无 token/坏 token 401，全部符合预期。

## 15.3 前端认证

### 背景思考

后端认证（15.1）和数据云端化接口（15.2）都就绪了，但前端还是"无账号"状态：所有个人数据直接读写 localStorage，用户不知道自己有没有登录。15.3 把认证接到前端：登录/注册页、全局登录态、路由守卫，让"登录后才能用学习功能"这件事立起来。

### 完成内容

- **`api/auth.ts`**：`register/login/fetchMe` + token 存 localStorage（key `de.authToken.v1`）；错误统一抛后端 `detail` 消息（如"邮箱或密码错误"）。
- **`context/AuthContext.tsx`**：`AuthProvider` 启动时若有 token 就 `fetchMe` 恢复登录态（`loading` 期间页面不渲染内容，避免闪登录页）；提供 `user/loading/login/register/logout`。
- **页面**：`LoginPage`（登录成功后跳回来源页，靠 `state.from`）+ `RegisterPage`（密码≥6 位校验）。
- **`ProtectedRoute`**：未登录访问个人数据页 → 重定向 `/login` 并记住来源；登录页/注册页不受保护。
- **路由调整**：`/vocabulary` `/review` `/dashboard` 用 `ProtectedRoute` 包裹；`/` `/articles/*` `/new` `/login` `/register` 公开。
- **`SiteHeader`**：未登录显示"登录"按钮；已登录显示用户名 + 退出按钮，并只在登录后显示"我的学习/生词本/复习"导航。

### 技术决策及理由

1. **AuthProvider 用 context 而非在每页各自 fetch**：登录态是全局一次性状态，context 最自然；路由守卫和 header 都能同步读到。
2. **恢复登录态用独立 `fetchMe`**：登录接口只返回 token，用户信息再单独拉一次，避免把用户信息塞进 token 或重复存储。
3. **redirect 用 `location.state.from`**：react-router 的标准做法，登录完成后跳回用户原本想去的页面，而不是一律回首页。

### 踩坑记录

- **CDP 测试"退出后错误密码不弹提示"的假阴性**：logout 后 `navigate('/')` 回到了文章页，测试脚本还在往 `#email` 填值、对 `document.querySelector('form')` 调 `requestSubmit()`——页面根本没有表单，静默失败。**教训：脚本断言前要先确认当前 URL/元素存在，否则会得出"功能坏了"的错误结论。**

### 验证（CDP 全流程）

用 headless Chrome + CDP（`Runtime.evaluate` 模拟填表/点击）跑通：

1. 注册新用户 → 自动登录 → 跳回 `/`，header 显示用户名 + 退出
2. 刷新页面 → 登录态保持（token 持久化 + fetchMe 恢复）
3. 登录态访问 `/vocabulary` → 正常进入
4. 退出 → token 清除
5. 未登录访问 `/vocabulary` → 重定向 `/login`
6. 正确账号密码登录 → 跳回 `state.from`（`/vocabulary`）
7. 错误密码 → 页面显示"邮箱或密码错误"，停留在登录页

测试后清理了 CDP 注册的 `cdpuser`，只留 `tester`。

## 15.4 数据切换 + 迁移

### 背景思考

15.3 之后登录态立起来了，但生词/收藏/阅读记录依然读写 localStorage——登录和没登录没区别，换设备数据也没法带走。15.4 的目标：登录后个人数据走云端 `/api/me/*`，未登录继续用本地；登录时把历史 localStorage 数据**一次性迁移**到云端。

### 完成内容

- **后端小改动**：`VocabCreate` 增加可选 `card`（生词可带 FSRS 卡创建）、`ReadingIn` 增加可选 `read_at`（阅读记录可带原始时间戳）——这两个都是迁移保真用的。
- **`api/me.ts`**：云端客户端，所有 `/api/me/*` 请求自动带 `Authorization: Bearer`。
- **`context/UserDataContext.tsx`**：数据层核心。
  - 未登录 → 直接读写 localStorage（保持原有行为）。
  - 登录 → 从 `/api/me/data` 拉全量进 state；所有写操作走云端 + 更新本地 state。
  - **自动迁移**：登录后首次加载，把本地生词/收藏/阅读记录里云端没有的项逐个推上去，成功后清空本地三个 key（`clearLocalUserData`）。
- **页面改造**：`ArticleCard`（已读/收藏）、`ArticleReader`（点词收藏生词）、`ArticleDetailPage`（进度保存/恢复/已读）、`DashboardPage`（统计 + 迁移提示横幅）、`VocabularyPage`（增删/导入导出）、`ReviewPage`（FSRS 复习）全部改用 `useUserData()`。
- `ReadingRecord` 类型从 storage.ts 上移到 `types/index.ts` 共享。

### 技术决策及理由

1. **UserDataContext 一个数据源**：所有个人数据页面统一从 context 读，登录态切换时数据源自动切换，页面代码不用关心"现在在哪"。
2. **迁移只补缺失项**：用云端已有集合做差集，只推本地有而云端没有的，避免重复/覆盖用户已有的云端数据。
3. **等待 auth 恢复再决定数据源**：最初 `loading` 初始为 false，auth 恢复期间会误读空 localStorage（见踩坑）。
4. **前端保证生词永远有合法 FSRS 卡**：`newCard()` 兜底，避免云端出现 `card: {}` 导致复习页永远不排期。

### 踩坑记录

**ReviewPage 空队列假象**：登录态下打开 `/review` 永远显示"今天没有待复习的生词"。根因是数据异步加载——UserDataContext 在 auth 恢复完成前 `loading=false` 且从空 localStorage 初始化，ReviewPage 挂载时 `useState(() => vocabulary.filter(...))` 就抓了个空快照。两处修复：
1. 数据源决策前先等 `authLoading` 结束（context 里 `if (authLoading) return`）；
2. ReviewPage 改成 `loading` 就绪后再取一次快照（`useEffect` + `snapshotRef`）。

**生词 `card: {}` 静默损坏 FSRS**：点词收藏走云端路径时没建 FSRS 卡，后端 `card` 默认 `{}`，这类词 `isDue({})` 永不为真、`review({})` 直接 NaN。修复：`addVocabulary`/`importVocabulary` 云端路径统一用 `newCard()` 兜底。

**ArticleDetailPage 滚动 effect 依赖 `reading` 导致无限循环**：`saveProgress` 会改 `reading` state → effect 重新执行 → 重新挂监听 → 清理时又 `markRead` → 又改 state…… 用 ref 保存最新回调（`saveProgressRef`/`markReadRef`），effect 依赖保持 `[loading, article?.id]` 稳定。

### 验证（CDP 全流程）

1. 未登录在 localStorage 制造生词（含完整 FSRS 卡）+ 收藏 `[1,2]` + 阅读记录
2. 登录 tester → 云端出现 `migrateword`、收藏 `[1,2]`、阅读记录，本地三个 key 已清空，FSRS 卡完整保留（`due/stability/difficulty/...` 原样）
3. 云端阅读记录保留原始 `read_at`（`2026-08-02T09:30:00`）
4. dashboard 显示"本机旧数据已同步到云端"横幅 + 正确统计
5. `/review` 正确列出到期生词，点"良好"后 FSRS 卡写入云端（`reps+1`、`due` 推到 11 天后）
6. 阅读文章 44 → 滚动保存进度 `0.59` → 离开 markRead → 列表显示"已读"徽章
7. 文章卡片收藏按钮 → 云端 bookmarks 加 44

测试数据全部清理，`tester` 云端数据归零。

## 15.5 个人后台

### 背景思考

15.4 之后个人数据能云端同步了，但用户没有地方管理自己的账号和数据的"存档/清空"。15.5 补上个人后台：账号信息（改用户名、改密码）+ 数据管理（导出云端数据备份、一键清空）。

### 完成内容

- **后端**：
  - `PATCH /api/auth/me`：改用户名（校验不与他人冲突）
  - `POST /api/auth/change-password`：改密码（先验旧密码）
  - `DELETE /api/me/data`：清空当前用户全部个人数据（三表 delete）
- **前端 `SettingsPage`（`/settings`，受保护路由）**，三个区块：
  1. **账号信息**：显示邮箱 + 改用户名（成功后 `refreshUser` 同步 header）
  2. **修改密码**：旧密码 + 新密码，错误提示原密码不正确 / 密码至少 6 位
  3. **数据管理**：实时统计云端数据量（生词/收藏/阅读）、导出 JSON 备份、一键清空（需二次确认）
- `AuthContext` 增加 `refreshUser`（改用户名后重拉用户信息）；header 用户名可点击进设置页。

### 技术决策及理由

1. **`DELETE /api/me/data` 走 `sqlalchemy.delete` 批量删**：不用逐条 ORM 删，一次三句 SQL 搞定，SQLite 下也快。
2. **导出走前端侧聚合**：数据本来就在 context 里，前端直接 `JSON.stringify` 成文件，不用后端再开一个导出接口（`GET /api/me/data` 已经是全量）。
3. **清空需二次确认**：破坏性操作，先按钮变"确认清空/取消"，避免误触。
4. **改密码不强制重登**：JWT 7 天有效，改密后老 token 仍可用（个人项目接受此简化，文档说明）。

### 踩坑记录

**改用户名后 header 不刷新**：`PATCH /api/auth/me` 只改数据库，AuthContext 里的 `user` 还是旧的。新增 `refreshUser()`（内部 `fetchMe`）在保存成功后调用，让 header 显示新用户名。

**CDP 验证脚本自身的坑**：`Runtime.evaluate` 传多行函数体时顶层 `return` 会报 `Illegal return statement`——脚本里用 `(function(){...})()` 包裹；headless 默认手机视口导致 `hidden sm:inline` 的用户名不渲染，验证 header 要看 API 返回而非 DOM 文本。

### 验证（CDP 全流程）

1. 设置页三区块渲染正常
2. 改用户名 → `fetchMe` 返回 `tester_renamed`，header 同步
3. 错误旧密码 → 显示"原密码不正确"
4. 正确旧密码 → "密码已更新"，退出后用新密码登录成功（跳回设置页）
5. 造数据 → 点清空 → 二次确认 → 云端三表归零

测试后恢复 `tester` 用户名/密码，数据归零。（注：库里另有一个 `matrix` 用户及数据，为真实用户所有，未触碰。）
