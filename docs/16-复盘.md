# 阶段 16：全流程复盘

> 从 8 月 4 日第一次提交到 8 月 5 日用户体系收尾，两天、24 次提交、约 5300 行代码。这篇把整个项目从零到"能用"的过程过一遍：当初为什么这么规划、实际做的时候哪些和预期一样、哪些走偏了、踩了哪些坑、回头看有哪些可以做得更好。也是博客文章的素材库。

## 一、项目最终长什么样

**DailyEnglish**：个人英语阅读学习网站，前后端分离全栈项目。

- **数据规模**：44 篇文章（内置 4 + VOA 30 + 卫报 5 + 大西洋月刊 5）、2 个用户
- **代码量**：前端 TS/TSX 约 3800 行，后端 Python 约 1500 行，共约 5300 行
- **功能清单**：

| 模块 | 功能 |
|---|---|
| 文章浏览 | 列表（搜索/难度/来源筛选/排序/加载更多）、详情页（正文排版/点词查词/进度恢复） |
| 内容源 | 内置语料 + 三个爬虫来源（VOA/卫报/大西洋），可插拔 provider 架构，每源风控 + 熔断 |
| 学习工具 | 逐词点查（dictionaryapi.dev + 本地缓存）、生词本（导入导出）、FSRS 间隔复习 |
| 学习记录 | 已读标记、阅读进度、收藏、统计页（累计/本周/词数） |
| 用户体系 | 注册/登录（JWT）、数据云端化、登录自动迁移本地数据、个人设置（改密码/导出/清空） |
| 工程化 | 定时抓取、抓取异步化、self 精读（粘贴文章）、部署配置（Nginx + systemd + 发布脚本） |

## 二、当初的规划 vs 实际

对照 `01-项目规划.md`，把"说好的"和"实际发生的"摆在一起看，偏差最有价值。

### 2.1 对得上的

1. **技术栈一次没换**：Vite + React + TS / FastAPI + SQLAlchemy + SQLite 从头用到尾，没中途推翻重来。当初选型的理由（展示型 SPA 用不上 Next.js、前后端分离利于学习）在实践里都站得住。
2. **MVP 边界守住了**：规划说"MVP 只做展示型，一切要写库的交互后置"。实际确实先纯前端 mock + 只读接口跑通全链路，生词本/学习记录都是后面才加的。
3. **SQLite 扛住了**：规划里担心多用户并发，实际到阶段 15 加了用户体系+云端数据，SQLite 依然无压力（个人项目场景）。当初"怕过度设计所以不用 MySQL"的决定被验证是对的。
4. **AI 协作模式**：AGENTS.md 从第一天就约定"每个阶段独立文档 + PROGRESS 索引 + stage 提交"，这套机制 24 次提交一次没破，成了整个项目的骨架。

### 2.2 走偏的 / 超出预期的

1. **MVP 之后的走向和规划完全不同**。规划阶段的"未来规划"里根本没有爬虫、没有用户体系——实际上：
   - 阶段 10~11 **加了爬虫**（这是最大的一次扩编，从一个只读展示站变成了会自己"进货"的内容站）
   - 阶段 15 **加了完整用户体系**（规划里明确写"❌ 不做账号登录"，结果做了，还做了 5 个子步骤）
   - 结论：**MVP 阶段"不做 X"的边界不是永久的，是"现在不做"。项目长到一定阶段，这些功能自然会回来。**

2. **版权策略从"绕开"变成"承担风险"**。规划写"不用有版权文章，用公版内容"。实际 VOA 是公有领域，但卫报/大西洋月刊抓的是完整正文（有版权）。这是用户明确知情后决定接受的（个人学习用途），并写进了文档。复盘要点：**项目的合规底线可以在"私有使用"前提下调整，但如果将来公开部署，这是必须回头处理的一笔技术债。**

3. **"学全栈"的目标超额完成但也暴露了范围蔓延**。阶段 09 到 15 之间，功能越加越多，一度接近"给自己找麻烦"的状态。好在这个项目是学习驱动，功能多=知识点多，但回头看有些功能（比如自我精读/粘贴文章）使用频率存疑。

## 三、技术决策复盘（哪些选择是对的）

### 3.1 值得肯定的决策

1. **前后端彻底分离 + DTO 映射层**（阶段 07）：后端字段是 `snake_case`、前端用 `camelCase`，所有映射集中在 `api/articles.ts` 的 `toArticle()`。后期后端加了 `source`/`source_url`/用户体系，前端只改这一个文件。**数据层的"唯一入口"是后期大量改动的安全垫。**
2. **爬虫可插拔 provider 架构**（阶段 11）：`base.py` 抽象基类 + `registry.py` + 每个来源一个文件 + 每源限速/退避/熔断。加一个新来源 = 一个文件 + 一行注册。没有这个抽象，后面根本不敢碰卫报（正文藏在 `div[data-gu-name]`）和大西洋（正文在 Next.js `__NEXT_DATA__` GraphQL 里）这种硬骨头。
3. **FSRS 用官方库而不是手写公式**（阶段 12）：`ts-fsrs` 一个 import 就拿到正经的间隔重复算法，比自己拍脑袋写的三级间隔科学得多，成本几乎为零。
4. **数据层 context 化**（阶段 15.4）：`UserDataContext` 让"登录走云端、未登录走本地"对页面完全透明，6 个页面/组件一个 hook 全部接入，迁移逻辑只写一遍。
5. **轻量幂等迁移**：`migrate()` 只补列、`create_all` 只建缺的表、seed 幂等、爬虫按 URL 去重——**整个项目没有一个"必须重建库"的版本**，数据库文件从阶段 06 一路活到 15，这在"边学边做反复改"的项目里很不容易。
6. **验证驱动开发**：每阶段都用 curl（后端）和 headless Chrome + CDP（前端交互）实测通过才提交。前端交互（点词、翻卡、登录跳转）不写自动化测试，全靠 CDP 模拟点击验证，成本低效果好。

### 3.2 踩过的坑（按"坑的性质"归类，比按阶段更有效）

**环境类（WSL 特有，占了快一半的坑）**
- WSL 挂载盘 mtime 精度问题：vite dev 会喂**旧代码**，改完代码必须 `pkill -f "[v]ite"` + 清 `node_modules/.vite` + 重启。这是最坑的一个，反复出现。
- `pkill -f` 带方括号/模式会匹配到自身 bash 包装进程，导致命令超时甚至连带杀掉刚启动的后台服务 → 杀进程和启动必须**分两条命令**。
- 后台服务要用 `setsid nohup ... </dev/null >log 2>&1 &` 脱离，否则 bash 命令超时会把服务一起带走。
- 无 sudo 环境：Python 用 `~/.local` 的 pip + virtualenv，装包全走清华镜像。
- headless Chrome 从 WSL 启动要用 Windows 路径的 `--user-data-dir`，CDP 连接要用新版 websockets（旧版 8.x 和 Python 3.10 asyncio 不兼容）。

**框架/库类**
- lucide-react 1.28 把 `Loader2` 改名为 `LoaderCircle`，import 了旧名直接白屏。
- FastAPI 嵌套响应模型不会自动 `from_attributes=True`，手动构造 `MeData` 嵌套 ORM 对象时 500。
- FastAPI 新版把 include 的路由包成 `_IncludedRouter`，用 `r.path` 检查路由是看不到的（一度误判路由没生效）。
- `EmailStr` 需要运行时装 `email-validator`，不装 uvicorn 启动直接 ImportError。
- SQLite 的 DateTime 不收字符串，要 `datetime.fromisoformat` 转换。
- ts-fsrs 的 `scheduling[rating]` 需要类型断言。

**逻辑类（自己写的 bug）**
- 前端 `toArticle` 漏映射 `content` 字段 → 详情页正文为空。
- 来源筛选 tab 塌缩：把"服务端过滤"和"前端渲染层过滤"混在一起，最后确定 source 过滤放渲染层。
- 登录态下 `ReviewPage` 永远空队列：数据异步加载，组件挂载时抓了空快照 → 等数据就绪再取一次。
- 云端生词 `card: {}` 破坏 FSRS：在线添加路径忘了建卡 → `newCard()` 兜底。
- `ArticleDetailPage` 滚动 effect 依赖 `reading` state → 保存进度改 state → effect 重跑 → 无限循环 → 用 ref 存最新回调。

## 四、工程习惯复盘

1. **提交规范的价值远超预期**。`feat:/fix:/docs: + stage: N` 的约定让 24 次提交可检索、可回滚、可讲成一条故事线。知识库侧也能靠 `git log` 直接同步进度。
2. **文档即素材**。16 个阶段文档都是口语化记录（"背景思考/完成内容/技术决策/实际命令/踩坑/下一步"），这是最被低估的产出——**博客文章不用"写"，只要"整理"**。
3. **复盘时才发现的技术债**：
   - `requirements.txt` 停在 3 个包，实际用了 10 个（apscheduler/pyjwt/bcrypt/requests/bs4/email-validator/pydantic 都没记录）→ 本次复盘已修复。**教训：加依赖时同步更新 requirements，别等部署那天才暴露。**
   - `SECRET_KEY` 是硬编码开发值，公开部署前必须换成环境变量。
   - 卫报/大西洋全文有版权，公开部署前需要换成官方 API 或只留摘录。
   - README 至今是占位符（规划里也记了这条）。
4. **测试**：项目没有单元测试/前端测试框架，靠的是每阶段的 curl + CDP 手工验证。对学习项目够用，但**如果要把这个项目当"作品"展示，补一个最小测试集（后端 pytest 冒烟 + 前端至少一个组件测试）是加分项**。

## 五、学习收获（按"学到的东西"归类）

1. **全栈链路**：从 Vite 脚手架 → 组件 → 路由 → 状态 → API → ORM → 数据库 → 部署，整条链路走通了一遍，这是看教程替代不了的。
2. **架构抽象**：爬虫 provider 的可插拔设计、"数据层唯一入口"（DTO/context）、幂等迁移，这些是"写得多之后才知道为什么要这么做"的知识点。
3. **真实世界的数据**：HTML 抓取（卫报）、Next.js 内嵌 JSON（大西洋）、限速/熔断——教科书不会教这些，都是实际踩出来的。
4. **环境工程**：WSL 的 mtime/pkill/后台进程这些"环境级"坑，比写业务代码更能体现一个开发者的经验值。
5. **与 AI 协作的方式**：把约定写进 AGENTS.md、让 AI 每阶段产出独立文档、用 CDP 让 AI 自己验证前端交互——这套"AI 辅助开发的协作协议"本身就是收获。

## 六、如果重来一遍 / 下一步建议

### 如果重来（按优先级）

1. **加依赖就更新 requirements.txt**（这次已修）。
2. **数据模型一开始就设计用户隔离**：阶段 15 加用户体系时，前期 localStorage 数据要做迁移。如果知道后面要做账号，可以更早定好"个人数据归属"的抽象。不过这也符合"边学边做"——当时没账号需求，硬设计反而过度。
3. **早期就引入一个极简 E2E 验证脚本**：CDP 验证每次都要重写脚本，前期抽出一个可复用的"登录+点词+复习"脚本能省不少时间。

### 下一步（按价值排序）

1. **写 README + 真实部署**（阶段 08 配置已就绪，等服务器/域名到位）：这是"作品"的最后一步。
2. **公开部署前处理技术债**：SECRET_KEY 环境变量化、卫报/大西洋版权合规（换官方 API 或摘录）、HTTPS。
3. **补最小测试集**：后端 pytest 冒烟（health/articles/auth/me）+ 前端一个组件测试。
4. **做视觉打磨**：目前功能全但视觉朴素，可以用已装的 impeccable skill 做一轮精修（这也是阶段 01 规划里"阅读体验是灵魂"的延续）。
