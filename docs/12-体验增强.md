# 阶段 12：体验增强（定时抓取 + 抓取异步化 + 真 FSRS 闪卡）

> 本阶段落地三件"低成本高价值"的增强：定时增量抓取、抓取任务异步化、用 FSRS 算法替换简化闪卡。

## 背景思考

爬虫三源（VOA/卫报/大西洋）就绪后，实际用起来还有三个短板：

1. **抓取靠手动**——每次都要点"同步外部文章"，而且全源抓一遍要 1 分钟以上，`POST /api/crawl` 同步阻塞，前端一直转圈
2. **闪卡是简化版**——1/3/7 天三级固定间隔，不科学，复习计划不该是拍脑袋的
3. 没有定时自动拉新文章的能力

于是定这三件一起做：**定时抓取**（APScheduler 每天自动增量）、**抓取异步化**（后台任务 + 轮询）、**真 FSRS**（`ts-fsrs` 库，替代手写三级）。

## 完成内容

### 1. 定时增量抓取（APScheduler）
- 后端 `main.py` lifespan 里启动 `BackgroundScheduler`，每天 **08:00（Asia/Shanghai）** 触发抓取
- 定时任务走与手动相同的 `CrawlScheduler`（单例串行），风控/去重全复用
- 已有抓取在跑时，定时任务自动跳过本次，不叠加并发

### 2. 抓取异步化（后台任务 + 状态查询）
- `backend/app/crawler/tasks.py`：`CrawlScheduler` 单例
  - `start(sources)`：后台线程跑抓取，立即返回 `task_id`；**串行**（同一时间只跑一个，避免 SQLite 并发写冲突）
  - `get(task_id)`：查任务状态（running/done/error + 结果统计）
  - `trigger_daily()`：定时任务入口，已运行则跳过
- 接口改造：`POST /api/crawl` → 立即返回 `{task_id, status}`（不再阻塞）；`GET /api/crawl/status/{task_id}` → 轮询状态与各源统计；已有任务在跑时返回 **409**
- 前端同步按钮：POST 拿 task_id → 每 2 秒轮询 → done 后刷新列表并提示新增数

### 3. 真 FSRS 闪卡（ts-fsrs）
- 安装 `ts-fsrs`（TypeScript FSRS 实现）
- `frontend/src/lib/fsrs.ts`：封装 `newCard()`（createEmptyCard）、`review(card, rating)`（FSRS 四档调度）、`isDue()`
- `VocabEntry` 新增 `card: FSRSCardData` 字段（due/stability/difficulty/reps/lapses/state 等）；**旧数据自动迁移**（读 localStorage 时若无 card，用旧 nextReviewAt 重建）
- 复习页改为 FSRS 标准**四档**：忘记(Again) / 困难(Hard) / 良好(Good) / 简单(Easy)，不再只是"没记住/记住了"
- 生词本页状态徽章改用 FSRS state（新词/学习中/复习中/重学中）

## 技术决策及理由

1. **后台线程而非队列框架**：单进程 + SQLite 的个人项目，`threading.Thread` + 内存 dict 足够，不引 Celery/RQ 这类重依赖。
2. **串行抓取**：手动 + 定时可能同时触发，SQLite 写并发会锁冲突，用一个 `_running` 标志强制串行 + 409 拒绝，最简单可靠。
3. **APScheduler 进程内跑**：项目部署用 systemd 托管 uvicorn（阶段 08），scheduler 随进程启动，不用额外 crontab，跨平台一致。
4. **用库不手写 FSRS**：FSRS 公式复杂（稳定度/难度/可提取性迭代），`ts-fsrs` 是官方社区实现，直接调用避免自己推公式出错。
5. **旧数据迁移**：localStorage 里已有旧的 stage/nextReviewAt 生词，读时惰性迁移成 FSRS 卡，用户无感升级。

## 实际命令

```bash
# 安装依赖
./.venv/bin/pip install apscheduler -i https://pypi.tuna.tsinghua.edu.cn/simple
npm install ts-fsrs --registry=https://registry.npmmirror.com

# 后端重启后验证异步抓取
curl -X POST http://localhost:8000/api/crawl          # → {task_id, status:"running"}
curl http://localhost:8000/api/crawl/status/<task_id> # → 轮询直到 done

# 单测 FSRS 调度（Good→10min→2天，Again→重学）
node --input-type=module -e "import {createEmptyCard,fsrs,generatorParameters,Rating} from 'ts-fsrs'; ..."
```

## 踩坑记录

- **`pkill -f "[v]ite"` 会超时/误杀**：bash -c 包装进程的命令行里含有 `[v]ite` 字面，`pkill -f` 匹配正则 `vite` 会命中自身的包装进程，导致命令挂起甚至把刚启动的服务一起杀掉。规避：pkill 与启动命令**分两条**执行，先彻底 pkill + sleep，再单独启动。
- **uvicorn 新进程被连累**：pkill + 启动放同一条命令时，工具超时（sleep 太久）会把后台 uvicorn 也带走。教训：启动命令要短、不 sleep；等待就绪用单独的轮询命令。
- **ts-fsrs 类型索引报错**：`scheduling[rating]` 中 `Rating` 是 enum，不能直接索引 `IPreview`，需 `as unknown as Record<number, { card: Card }>` 断言。
