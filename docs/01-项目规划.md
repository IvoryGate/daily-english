# DailyEnglish 项目规划

> 本文档是「阶段 01 项目规划」的详细记录，口语化、偏学习笔记风格，供后续整理博客文章积累素材。
> 规划会随开发推进不断调整，这里记录的是**为什么这么选**，而不是一成不变的结果。

## 1. 这个产品到底做什么

一句话：**一个给自己看的英语阅读学习网站**。

学英语最怕什么？怕坚持不下来，怕没有合适的阅读材料，怕读的时候被生词卡住没有顺手查词的地方。这个网站就是想解决"每天随手读一篇英文"这件事：

- 打开网站，看到一个文章列表，选一篇开始读
- 文章就是普通英文短文，排版舒服一点，手机上也能看
- 读完就完了，不搞复杂的打卡、统计、用户体系

### 为什么做这么简单（很重要）

一开始我（我=开发者，同时也是学习者）想得挺多：要用户注册、要生词本、要笔记标注、要阅读曲线…… 但冷静下来有几个现实约束：

1. **服务器资源有限**。买的是最便宜的云服务器，内存也就几百 MB。给每个用户开账号、存笔记，多用户并发一上来就扛不住，纯属给自己找麻烦。
2. **这是一个学习项目，不是创业项目**。目的不是做产品，是**学全栈**。功能做太多，后面全在写业务逻辑，反而学不到基础设施的东西。
3. **边学边做，要能跑起来**。第一个能点开看的版本越早越好，先有正反馈，再慢慢加东西。

所以砍到最后，MVP 只剩一件核心事：**把英文文章漂亮地展示出来，能读**。

## 2. MVP 功能清单（阶段 02~07 的边界）

| 功能 | MVP 做不做 | 说明 |
|---|---|---|
| 文章列表页 | ✅ 做 | 标题 + 摘要 + 难度 + 标签，从上往下选着读 |
| 文章阅读页 | ✅ 做 | 正文排版、上一篇/下一篇、字数/预计阅读时间 |
| 内置语料 | ✅ 做 | 先内置 20~30 篇英文短文，用脚本灌进数据库 |
| 查词/生词本 | ⏸️ 后置 | 需要持久化交互，MVP 阶段不做 |
| 笔记/标注 | ⏸️ 后置 | 同上，等有账号体系或本地存储再说 |
| 账号登录 | ❌ 不做 | 单用户无登录，省掉一整套鉴权 |
| 阅读统计/打卡 | ⏸️ 后置 | 对"学全栈"没增量，先放着 |

> 一句话原则：**MVP 只做"展示型"功能，一切要写数据库的交互全部后置**。这样后端只需要"读"，不需要"写"，SQLite + FastAPI 轻松扛住，还能把每一层的知识都学扎实。

## 3. 技术选型：为什么是这一套

> 课程参考《零到全栈：AI时代的全栈开发》（李勃老师）。技术栈前后端分离，各自独立开发、再联调。

### 3.1 前端：Vite + React + TypeScript

- **Vite 做脚手架**：启动快、热更新爽，生态成熟，官方模板直接生成 React + TS 项目，不用自己配一堆东西。
- **React 做框架**：课程主推，社区最大，找工作/看资料都绕不开，组件化思路也最直观。
- **TypeScript 做语言**：全栈项目里前后端类型一致化很重要，写的时候多花一点时间，跑起来少一堆 bug。这也是课程强调的。

### 3.2 UI：Tailwind CSS + shadcn/ui

- 样式的坑大家都懂：手写 CSS 慢，Ant Design 这类库又太重、改起来费劲。
- **Tailwind** 是原子化 CSS，写起来像拼积木，改样式不用切文件。
- **shadcn/ui** 不是传统组件库——它把组件源码直接复制进你的项目，代码完全可控，不会出现"想改个按钮颜色要翻几层覆盖"的破事。而且它底层是 Radix，无障碍（键盘导航、读屏）都给你做好。
- 配套前面装的前端设计 skill（taste-skill、impeccable），正好避免做出"一眼 AI 味"的界面。

### 3.3 后端：FastAPI + SQLAlchemy + SQLite

- **FastAPI**：Python 里现在写 API 最舒服的框架，自带交互式文档（Swagger UI），调试接口不用装 Postman。类型提示（type hint）驱动，和 TypeScript 的思路一脉相承。
- **SQLite**：单机、零配置文件、就是一个文件，完美契合"单用户、数据量小"的项目。等以后真需要换 MySQL/PostgreSQL，SQLAlchemy 可以平滑迁移。
- **SQLAlchemy**：Python 最主流的 ORM，把表和 Python 对象对应起来，SQL 都不用手写。

### 3.4 为什么不用 Next.js 了

最早计划里写的是 Next.js，但实际梳理后发现：

- 本项目是**纯展示型 SPA**，没有 SEO 需求（不指望被搜索引擎收录），没有服务端渲染的必要。
- 课程主线是"前后端分离"：前端归前端、后端归后端，**Next.js 全栈框架反而模糊了这个学习边界**，把 FastAPI 和数据库的学习目标冲淡了。
- Vite 更轻、更聚焦，学到的也是通用前端技能，以后换任何框架都不亏。

> 结论：Vite + React + TS 承担"前端"，FastAPI + SQLite 承担"后端"，各学各的，最后联调。

> 关键约定：**前后端彻底分离**，前端只通过 HTTP 接口拿数据，绝不直接碰数据库文件；后端只管接口和数据，不管页面。

## 5. 数据模型（MVP 就一张表）

MVP 的数据库就一张 `articles` 表，朴素但够用：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | 自增主键 | 文章 ID |
| title | TEXT | 标题 |
| excerpt | TEXT | 摘要，列表页用 |
| content | TEXT | 正文（纯文本或轻量 Markdown） |
| difficulty | TEXT | 难度：beginner / intermediate / advanced |
| tags | TEXT | 逗号分隔的标签，如 "science,tech" |
| read_time_minutes | INTEGER | 预计阅读分钟数（选填） |
| created_at | DATETIME | 创建时间 |

> 为什么 tags 用逗号分隔而不是单独建表？MVP 阶段查询简单，逗号分隔够用；以后要按标签筛选再做多对多，别过度设计。

## 6. API 设计（MVP 只有三个接口）

```
GET /api/health              → {"status": "ok"}         # 健康检查，部署时验证用
GET /api/articles            → 文章列表（含摘要、难度、标签）
GET /api/articles/{id}       → 文章详情（含完整正文）
```

全部是**只读**接口，符合"展示型 MVP"的定位。前端开发时不用等后端，先用 mock 数据，联调阶段再切真接口。

1. 先有**环境**才能写代码（02）
2. 前端和后端**各自并行**开发（03~06），前端用 mock 数据、后端用 curl 测，互不阻塞

## 8. 风险与提前想好的事

- **内置语料版权**：不用有版权的付费文章，用经典公版短文（如 Aesop 寓言、经典散文）或自己写，避免法律麻烦。
- **未来要不要 Next.js（重要 FAQ）**：现在明确不用，因为纯展示型 SPA 用不上 SSR/SEO，而且课程主线非 Next.js。但"未来"若真出现需要 SEO（如被搜索引擎收录）或服务端渲染的场景，迁移路径是**成熟且低成本的**：React 生态通用，组件/hooks/类型/API 封装几乎全部复用，只需改路由写法、数据获取方式和部署方式（Node + Nginx）。到时候再迁移，不在现阶段提前背负 SSR 复杂度。此决策已与开发者确认。
- **阅读体验是灵魂**：文章阅读页的排版（字号、行距、最大宽度、夜间模式）比功能多少更重要，前端阶段要专门打磨，这是"和 AI 生成的模板页拉开差距"的关键。
- **README 至今是占位符**：等 MVP 定型后认真写一个，作为对外门面。
- **环境版本坑**：Node 版本、Python 版本、依赖版本都可能带来"我明明照着教程写的怎么跑不起来"，阶段 02 和 06 重点记录。
