# 阶段 28：词汇量估算 + 首页推荐词汇画像化

## 背景思考

阶段 27 给文章建立了词汇画像（`vocab_level` / `vocab_score`），让"这文章对用户是难是易"有了客观依据。但还差一块拼图：**用户自己的词汇量画像**。知道了"你会多少词、集中在哪几级"，才能精准说"这篇高级文章你还是别读了"。

第一阶段想得很直白：用户不是有生词本吗？那统计已掌握的词分布不就知道词汇量了。顺着这条线做了**词汇量估算曲线**，同时把首页"为你推荐"从「按游戏等级难度」升级成「按词汇画像区间」——阶段 27 那套级别区间函数正好复用。

## 完成内容

### 1. 后端：`vocab_estimate` 词汇量估算（`backend/app/gamification.py`）

核心是给用户算一个"估算词汇量 + 8 级掌握分布"。模型逻辑：

- **已掌握判定**：生词本里 FSRS `state>=2` 且 `reps>=3` 的词才算"已掌握"（不是所有收藏的都算）。
- **归级**：每个已掌握词经 `lemmatize`（词形归并）后，用 `level_of` 查它在 8 级词表中的级别。
- **单调外推**：由低到高逐级算"掌握比例" `r = 该级已掌握数 / 该级词表总量`。关键假设是**能力单调**——你会高级词必然也会低级词，所以每级有效比例取"从低级到当前级看到的最大值"（`running` 累积），防止某级生词多而把比例搞得不像话。
- **求和**：`估算 = Σ(每级词表总量 × 有效掌握比例)`，得到完整词汇量。
- **两个保护**：
  - **稀疏保护**：已掌握总数 `<10` 时统计无意义，不外推，直接返回已掌握数（避免 4 个词估出 46 这种假数）。
  - **底线**：估算值至少不小于实际已掌握总数。

词表规模常量 `_LEVEL_SIZE` 与后端 `word_lists.json` 实际词数对齐（junior 1603 → advanced 10556），避免硬编码漂移。

### 2. 接口：`/api/me/stats` 加 `vocab_estimate`

`backend/app/api/routes/me.py` 在 stats 返回里带上 `"vocab_estimate": vocab_estimate(db, user)`，结构为 `{estimate, per_level:[{level,label,total,owned}]}`。

### 3. 前端：Dashboard 词汇量卡片（`frontend/src/pages/DashboardPage.tsx` + `api/me.ts`）

词汇卡片从「生词累计曲线」升级为两栏布局：
- 左栏：**估算词汇量**大号数字（`stats.vocab_estimate.estimate`，无估算法麻 `stats.vocab_count`）+ 已掌握词数 + 近 3 月生词累计折线（沿用原 `LineChart`）。
- 右栏：**8 级分布进度条**，每级 `掌握% = owned/total` 渲染一条横向条（`bg-primary/70` 实色占比）。

### 4. 首页推荐词汇画像化（`frontend/src/pages/ArticleListPage.tsx`）

「为你推荐」从按 `stats.level.level` 查难度表，改为：
- 用 `vocabRangeForLevel(level)` 拿建议词汇画像区间（如 Lv1 → 初中），筛出 `vocabLevel` 落在区间的未读文章。
- 容错：区间内没文章时，回退到 `vocabLevel` ≤ `maxVocabForLevel(level)` 的跨档池（但排除 `advanced` 超纲）。
- 取 `vocab_score` 升序前三篇排出来——让用户先看最容易的。

## 技术决策及理由

1. **用"已掌握生词分布外推"而非阅读理解测试**：个人学习站没有标准标定样本，做不了客观量级，而生词本的掌握分布是最真实、零成本的行为信号。误差接受，但**方向**（你能读到哪一级）比绝对数更重要。
2. **能力单调外推**：用 cummax 而非逐级独立比例。因为某级个别词少（用户恰好没存那个级别的词）会给比例造假象，单调保证了"没涂完的低级"不被高级反超。
3. **稀疏保护**：小样本外推会系统性高估（4 个词估出 46），宁可不展示也不报假数——这在个人产品里比"精确但不真"更重要。

## 踩坑记录

1. **`db.scalars` 只取多列的第一列**！原来写的是
   `db.scalars(select(VocabularyEntry.word, VocabularyEntry.card))`
   然后 `for word, card in rows>`，运行时报 `too many values to unpack`——因为 `scalars()` 会把多列 select 压成单列（只返回第一列），展开成 2 元组的关系就没法解包。改为 `db.execute(...).all()` 才对。
   教训：**`.scalars()` 只适合单列 select**，多列要用 `.execute().all()`。

2. **偶尔忍不住想偷懒**：只要生词本所空就返回 0、一堆词再算正合适；但调到一半发现 4 个测试词估出 46，不装真实。加 `<10` 稀疏保护兜底后才合理化。

## 下一步
